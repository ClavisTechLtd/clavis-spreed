# Story 1.10: Threads orphaned by message expiry are reaped

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Clavis engineer,
I want a Thread to survive its root message being deleted but not survive it expiring,
So that thread rows do not accumulate forever and a warm cache cannot accept content into a Thread that no longer exists.

## Acceptance Criteria

**AC1**
**Given** a Thread whose Thread Root Message is deleted by its author or by a moderator
**When** the deletion completes
**Then** the comment row survives as a tombstone and the Thread survives with its id, state, lock reason and replies intact
**And** its root renders as the deleted placeholder.

**AC2**
**Given** message expiry, which hard-deletes comment rows
**When** the expiry job runs
**Then** a bounded reaper removes `talk_threads` and `talk_thread_attendees` rows whose root comment no longer exists.

**AC3**
**Given** a Conversation with a long history
**When** the reaper runs
**Then** it is bounded per run rather than a full-table sweep, alongside the existing five-minute expiry job.

**AC4**
**Given** a Thread is reaped
**When** the same pass completes
**Then** that Thread's cache entry has been invalidated
**And** `validateThread()` no longer answers from a warm entry, so content cannot be accepted into a Thread that no longer exists.

**AC5**
**Given** any read path encountering a Thread whose root comment is missing
**When** it renders or responds
**Then** it degrades the way `renameThread` already does rather than erroring.

**AC6**
**Given** an open upstream issue reports Threads persisting after all their messages are deleted — the same ground this reaper occupies
**When** a future upstream release lands its own fix
**Then** the reaper carries a comment naming this requirement so the collision is reconciled deliberately rather than discovered.

## Dev Notes

### Why this story is mostly new production code, unlike Story 1.9

Tracing the real code (not assumed) found: **AC1 and AC5 already work today** and need only regression coverage (no reaper exists yet, but nothing currently *breaks* on a missing root — see below). **AC2, AC3, AC4 and AC6 are a genuine, unimplemented gap** — there is no reaper anywhere in this codebase today. `grep -rn "orphan" lib/` returns nothing; `ExpireChatMessages` (`lib/BackgroundJob/ExpireChatMessages.php`) only calls `ChatManager::deleteExpiredMessages()` (→ `CommentsManager::deleteCommentsExpiredAtObject('chat', '')`, a genuine hard `DELETE FROM comments ...` in Nextcloud core, confirmed by reading `/var/www/html/lib/private/Comments/Manager.php:1596-1612` inside the verification container) and `ProxyCacheMessageService::deleteExpiredMessages()`. Neither touches `talk_threads` or `talk_thread_attendees` at all. Do not skip Tasks 1-3 on the assumption this is test-only, the way Story 1.9's AC1/AC2/AC5 turned out to be.

### AC1, AC5 — confirmed already working, by tracing the real path

- **AC1 (tombstone, not hard-delete):** `ChatManager::deleteMessage()` (`lib/Chat/ChatManager.php:696-750`) never removes the comment row — it rewrites `message`/`verb` (`VERB_MESSAGE_DELETED`) via `commentsManager->save($comment)` and leaves `id`, `actor_type`, `actor_id`, `topmost_parent_id` untouched. Since a Thread's id *is* its root comment's id (AD-5), and `ThreadService`/`ThreadMapper` never touch the comment row, the Thread row is completely unaffected by a soft delete. `findOrphanedThreadIds()` (Task 1.1) is safe by construction here: the `LEFT JOIN comments c ON c.id = t.id` still finds a row (tombstoned or not), so a soft-deleted root is never mistaken for orphaned. No production code change needed for AC1 itself — only the Behat regression test (Task 6.1, first scenario).
- **AC5 (degrade, don't error):** `ThreadController::prepareListOfThreads()` (`lib/Controller/ThreadController.php:376-440`), the single method every read path (`getThread()`, `getRecentActiveThreads()`, `getSubscribedThreads()`, `renameThread()`'s own response, `setState()`'s own response) funnels through, already tolerates a missing root: `$comments = $this->chatManager->getMessagesById($messageIds)` (→ `CommentsManager::getCommentsById()`, confirmed in core: `SELECT * FROM comments WHERE id IN (...)`, simply omits ids that don't exist — no exception) then `$first = $comments[$thread->getId()] ?? null; if ($first !== null) { ...build firstMessage... }` — a missing root just means `'first' => null` in the response, never an exception. `renameThread()` and `setState()` (lines 233, 337) independently wrap their own `chatManager->getComment()` call in `try { ... } catch (NotFoundException) { $comment = null; }` with the comment `// Root message expired, continuing without replying` — this is the literal "degrades the way renameThread already does" AC5 names. No production code change needed for AC5 — only the Behat regression test (Task 6.1, second scenario) pinning the specific mid-transition window (root hard-deleted, `talk_threads` row not yet reaped) that this story's reaper newly makes possible to reach in a live system (today it's unreachable because nothing ever deletes the comment row for real without also being tested against a live reaper).

### AC2, AC3, AC4, AC6 — the real gap, and the design decisions behind it

- **Where the reap logic lives:** a new sibling background job (`lib/BackgroundJob/ReapOrphanedThreads.php`), not a change inside `ExpireChatMessages`. Confirmed against the architecture spine (`ARCHITECTURE-SPINE.md`): the "Where the work lands" file tree lists `BackgroundJob/ # + orphaned-thread reaper (AD-5)` (a `+`, i.e. new file, using the same annotation convention as `Service/ThreadTagService.php # new`), and the Operational Envelope section states "This feature adds exactly two operational surfaces: one background reaper (AD-5) **alongside** the existing five-minute expiry job" — "alongside," not "inside." AD-5's own rule text ("the expiry job must also reap...") describes the *behavioural* requirement (expiry must be paired with reaping), not literally which class does it.
- **Orphan detection query** (`ThreadMapper::findOrphanedThreadIds()`): `LEFT JOIN comments c ON c.id = t.id WHERE c.id IS NULL LIMIT $limit`. Deliberately does **not** also join on `object_type='chat' AND object_id = t.room_id` (the stricter check `ThreadService::getRootComment()` uses for authority decisions) — `comments.object_id` is a `string` column (confirmed: `/var/www/html/core/Migrations/Version13000Date20170718121200.php:839-843`) and `talk_threads.room_id` is `BIGINT`; a column-to-column cast in a JOIN ON clause is markedly less portable across this app's supported DB engines than the `comments.id`-to-`talk_threads.id` numeric-to-numeric join (both integer family types, the same class of cross-width join Doctrine DBAL and this codebase already do elsewhere without incident). Per AD-5, a Thread's id *is* its root comment's id — that identity alone is what "root comment no longer exists" means; the object-type/object-id mismatch case `getRootComment()` additionally guards against is a defensive check against a stale/reused id belonging to a *different* object, which does not arise from the normal Thread lifecycle this reaper is scoped to. **Documented assumption** — flag in review if a future story finds this insufficiently strict.
- **"Bounded per run, not a full-table sweep" (AC3):** interpreted, per this codebase's own precedent (`SessionMapper::findSessionIdsWithoutAttendee()` / `CleanupStaleSessions`), as "every query carries a `LIMIT`, and one job run drains in bounded chunks rather than issuing one unbounded query" — not as "the underlying LEFT JOIN can never touch every `talk_threads` row in the worst case of zero orphans existing." That worst case (a full scan to conclude "nothing found") is an accepted, precedented cost in this codebase for exactly this shape of query and is not what AC3's Given/When ("a Conversation with a long history") is protecting against — it is protecting against the *reap* operation itself (the `DELETE`s) being unbounded, which chunking by `CHUNK_SIZE = 1000` prevents.
- **Cache invalidation ordering (AC4):** `remove()` happens for every orphaned Thread **before** the row is deleted (`ThreadService::reapOrphanedThreads()`, Task 2.1) so a reader racing the reaper observes, at worst, "cache says gone, mapper says still there for a moment" — never the inverse ("cache still warm, mapper says gone"), which is the one ordering that would let `validateThread()` (→ `findByThreadId()`, which reads-through the cache first) keep answering `true` for a Thread whose row was already removed. This mirrors `changeState()`'s existing "remove, never re-set" discipline (AD-1) one level up: reap is itself a kind of state change (Ongoing/Closed/Locked → gone), so it inherits the same cache-safety rule already established for every other Thread mutation in this file.
- **AC6 (upstream collision, named deliberately):** searched `nextcloud/spreed` issues (`gh issue list --repo nextcloud/spreed --search "thread orphan..."`) and found **#16739, "Delete empty Talk threads"** (open) — reports exactly the "ghost thread" symptom this reaper's ground occupies: a thread whose originating message was removed still exists, empty, with no way to clean it up. One important nuance for the code comment to state precisely: #16739's literal repro is a **soft**-deleted root (a user deletes their message via the UI) — which, per AD-5/AC1, this reaper deliberately does **not** reap (the Thread must survive a tombstone). This reaper only ever fires on a **hard**-deleted (expired) root. If/when upstream lands a fix for #16739's literal repro, it may be solving a related-but-distinct problem (or may generalize to cover this one) — the code comment (Task 2.2/3.3) exists so whoever reconciles that upstream change reads this distinction deliberately rather than assuming the two are identical and silently merging them.
