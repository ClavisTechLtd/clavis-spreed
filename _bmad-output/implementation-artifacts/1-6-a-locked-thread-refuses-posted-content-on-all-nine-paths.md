# Story 1.6: A Locked Thread refuses posted content on all nine paths

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a participant,
I want a Locked Thread to refuse content from wherever it arrives,
so that "locked" means locked rather than "locked unless you use a different button".

*Content reaches a Thread through nine distinct paths. Each is its own testable consequence because the first revision of the PRD enumerated six and missed three — the enumeration is the control, not a formality.*

## Acceptance Criteria

**AC1**
**Given** the guard is applied inside `ChatManager::sendMessage()` and `ChatManager::addSystemMessage()` and nowhere else
**When** it evaluates
**Then** it reads one expression, resolved once through the shared thread-id helper, **before** `commentsManager->save()`
**And** never on a value re-derived afterwards, because a refusal that happens after the save is not a refusal.

**AC2**
**Given** `sendMessage()`'s explicit-`threadId` branch, which today skips the `validateThread()` call the reply branch performs
**When** the asymmetry is closed
**Then** the guard is always handed a validated thread id.

**AC3**
**Given** a Locked Thread
**When** a typed message is posted into it *(path 1)*
**Then** it is refused with the `ThreadLocked` identifier, distinguishable by the client from a generic permission failure and from a Thread-not-found failure.

**AC4**
**Given** a Locked Thread
**When** a bot posts through the bot API *(path 2)*, or an in-process bot answers an invocation event *(path 3)*
**Then** each is refused, with a scenario per path.

**AC5**
**Given** a Locked Thread
**When** a rich object is shared into it *(path 4)*, or a poll is created in it *(path 5)*
**Then** each is refused, with a scenario per path.

**AC6**
**Given** a Locked Thread
**When** a file is shared into it *(path 6)* — the path that reads the thread identifier from share metadata and can create Threads as well as post into them
**Then** it is refused
**And** the scenario sits beside the existing file-share-into-thread scenario at `threads.feature:238-243`.

**AC7**
**Given** `ChatController::postAttachmentToRoom()`, which performs no thread validation whatsoever today
**When** the missing `validateThread()` call is added and an attachment is uploaded into a Locked Thread *(path 7)*
**Then** it is refused.

**AC8**
**Given** a Thread that is Locked at the moment of scheduling
**When** a participant schedules a message into it *(path 8)*
**Then** the request is refused at request time, where an acting participant still exists
**And** this carve-out is stated in the code rather than hidden, because scheduling writes no comment at all.

**AC9**
**Given** a message scheduled while the Thread was Ongoing, and the Thread Locked before the scheduled time
**When** the background job fires *(path 9)*
**Then** the message does not post, and the job marks it failed with a reason the sender can see
**And** the guard resolves and refuses without depending on request context, because this path has no live request and no acting participant.

**AC10**
**Given** a message scheduled while the Thread was Locked, then unlocked before its time
**When** it fires
**Then** it posts normally and, if the Thread was Closed, revives it per Story 1.5.

**AC11**
**Given** any refusal on any of these nine paths
**When** it occurs
**Then** it fails visibly rather than silently redirecting the content into the Conversation's main chat.

**AC12**
**Given** the state-change verbs of Story 1.4
**When** they write their system messages into a Locked Thread
**Then** they succeed, because the exemption is an explicit allow-list of those verbs and nothing else
**And** the exemption is **not** expressed as "system messages are exempt", which would leave four of these nine paths unguarded.

**AC13**
**Given** FR-5's enumeration is the control
**When** acceptance is written
**Then** there is **one integration scenario per path**, not one for the family.

### Assumption — the exemption list is `THREAD_MESSAGE_TYPES_WITH_CONTEXT` (six verbs), not AC12's literal four (documented, no interactive user available)

AC12 says "the exemption is an explicit allow-list of the state-change verbs... and nothing else." Read completely literally, that is `THREAD_LIFECYCLE_MESSAGE_TYPES` (four: closed/locked/reopened/unlocked). But `ThreadController::renameThread()`'s `thread_renamed` system message routes through the identical `addSystemMessage()` call shape and is **not** content by any reading of FR-5 — it is a management operation, structurally identical in kind to featuring, which FR-9's own text says explicitly "works on Closed and Locked Threads." Guarding it too would be an undocumented regression no AC asks for. Two readings were available: (a) implement AC12 with surgical literalism (four verbs only), accepting the rename regression as "not this story's problem since no AC mentions it"; or (b) widen the exemption to the pre-existing `THREAD_MESSAGE_TYPES_WITH_CONTEXT` constant (six verbs: the four plus `thread_created`/`thread_renamed`), which Story 1.4 already built and explicitly annotated for this kind of reuse.

**Resolution:** (b). Rationale: AC12's actual, stated *concern* is narrower than its literal wording suggests — it exists to prevent the exemption from being expressed as "system messages are exempt" (which would silently swallow the four content-carrying system-message paths, 4/5/6/7). A six-item, explicitly enumerated, pre-existing constant satisfies that concern exactly as well as a four-item one; neither is "all system messages are exempt." `thread_created` is inert (a thread that does not exist yet cannot be Locked) and `thread_renamed`'s inclusion is the one substantive addition, made to avoid a regression AD-2/FR-9 clearly do not intend and no AC requests. Flagged explicitly here per this skill's "document the assumption, continue" rule rather than silently choosing either reading.

### Assumption — pre-flight checks in `PollController`/`ChatController::postAttachmentToRoom()`/`scheduleMessage()` are a documented, necessary deviation from AC1's "nowhere else" (documented, no interactive user available)

AC1/AD-2 say the guard lives "inside `ChatManager::sendMessage()` and `addSystemMessage()` and nowhere else." Taken with total literalism, this would forbid any other call site from ever calling `ThreadService::ensureNotLocked()`. But three of the nine paths have a pre-write side effect that happens **before** either `ChatManager` method is ever called: `scheduleMessage()` writes no comment at all (AD-2's own named carve-out, AC8); `PollController::createPoll()` creates a `PollService` entity before its `addSystemMessage()` call; `postAttachmentToRoom()` moves a file out of the Draft folder before its `addSystemMessage()` call. For all three, waiting for the *sole* `ChatManager`-internal guard to fire means the side effect has already happened and — for poll/attachment — the resulting exception was previously being **silently swallowed**, which is precisely AC11's forbidden failure mode ("fails visibly rather than silently redirecting"), arguably worse for polls (reports success with an orphaned entity, not even a redirect).

**Resolution:** call `ThreadService::ensureNotLocked()` — the single shared *decision* — from these three additional call sites too, as a pre-flight check before the side-effecting operation. This does not create a second *implementation* of the Locked policy (that remains solely in `ThreadService`); it duplicates only the *call site*, exactly mirroring AD-2's own explicit precedent for path 8 (a second call site was always required and stated in code, "because scheduling writes no comment at all"). Poll-entity-creation and file-move are the same class of problem, extended here by direct engineering judgment rather than silently leaving AC11 broken for two of the nine paths. Documented at each Task (5.3, 7.3, 9.3) rather than only here.

### Assumption — path 6's exact refused status code is not independently verified (documented, no interactive user available)

`lib/Chat/SystemMessage/Listener.php`'s `file_shared` caller (path 6) has no controller to return an HTTP response from - it is a synchronous `ShareCreatedEvent` listener, and a thrown `LockedException` propagates uncaught exactly like `MessageTooLongException` already does at this same call site today (traced, not new). The Behat scenario for this path (Task 6.2) asserts `400`, matching this story's intended, distinguishable-refusal design for every other path - but the *actual* status code an uncaught exception produces here is decided by whatever generic exception handling exists further up Nextcloud core's Files Sharing API stack, which this story does not touch and Behat cannot execute here to confirm. If a real CI run shows this path actually surfaces as `500` rather than `400`, that is a pre-existing architectural gap this story's scope does not fully close for path 6 specifically (AC11's "fails visibly" still holds either way - a 500 is visible; AC3's "distinguishable" ideal would not, for this one path). Flagged explicitly rather than silently assumed verified.

### Race/idempotency note
