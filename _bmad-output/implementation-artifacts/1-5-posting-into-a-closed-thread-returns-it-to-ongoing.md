# Story 1.5: Posting into a Closed Thread returns it to Ongoing

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a participant with something to add,
I want posting into a finished Thread to simply revive it,
so that a premature close costs one message to undo and closing stays a habit rather than a decision.

## Acceptance Criteria

**AC1**
**Given** a Closed Thread and a participant who may post in the Conversation but is not a Thread Manager
**When** they post a reply into it
**Then** the reply succeeds and the Thread reports state Ongoing.

**AC2**
**Given** the revival happens
**When** the Thread's messages are read
**Then** no system message about the state change was produced — the reply itself is the record.

**AC3**
**Given** the revival hook is applied inside `ChatManager::sendMessage()` and `ChatManager::addSystemMessage()`
**When** content arrives by any of the eight live paths
**Then** every one of them revives the Thread, not only a typed message
**And** the effective thread id is resolved once through the single shared helper, before the write.

**AC4**
**Given** a message scheduled before the Thread was closed
**When** it fires into the Closed Thread
**Then** it posts and the Thread returns to Ongoing.

**AC5**
**Given** a Locked Thread and a non-manager participant
**When** they post
**Then** the post is refused and the Thread stays Locked — the asymmetry with Closed is deliberate.

**AC6**
**Given** the revival mutates the Thread
**When** the write completes
**Then** the cache entry is invalidated in the same pass
**And** a second actor reading the Thread sees Ongoing.

**AC7**
**Given** a participant viewing the recent-threads list filtered to live Threads
**When** a reply revives a Closed Thread
**Then** the Thread reappears in that list without the participant refreshing.

## Dev Notes

### Current state of the files this story touches (read in full during story creation)

**`lib/Chat/ChatManager.php`** (1365 lines) — `sendMessage()` (~383-513) and `addSystemMessage()` (~147-289) are the two methods AD-2 names as the exhaustive choke point for "posting content into a Thread." Both already resolve an effective `$threadId` and call `ThreadService::updateLastMessageInfoAfterReply($threadId, $messageId, $chat->getId())` — the return value (`$isThread`) is the existing, single source of truth for "this really is a live Thread," already computed once per call, before the method's `ChatMessageSentEvent`/`SystemMessageSentEvent` dispatch. This story hooks `ThreadService::reviveIfClosed()` in at that exact, already-existing point in both methods rather than introducing a new pre-save id-resolution helper: the id is not re-derived a second time, and the ordering (before the event dispatch) is what both methods already guarantee today. Confirmed by reading every caller of both methods (`ThreadController`, `ChatController::shareObjectToChat()`/`postAttachmentToRoom()`, `PollController`, `BotController`, `SendScheduledMessages`) that all eight content-writing paths from Story 1.6's nine-path enumeration funnel through one of these two methods — no controller-level change is needed for any of them.

**`lib/Service/ThreadService.php`** (453 lines post-Story-1.4) — `changeState()` (Story 1.4) is reused as-is for the actual mutation: it already does "mutate, then `cache->remove()`, never `set()`" (AD-1, AC6), and already no-ops if the target state equals the current one. This story adds `reviveIfClosed()` as a thin, state-checking wrapper in front of it, and does **not** modify `changeState()`'s behavior.

**`lib/Signaling/Listener.php`** (709 lines post-Story-1.4) — `notifyMessageSent()` (~548-598, the `ChatMessageSentEvent` handler, **distinct** from `notifySystemMessageSent()`, which Story 1.4 modified) already re-reads the Thread fresh via `findByThreadId()` for *every* regular chat message reply and embeds it via `$message->toArray('json', $thread)` — this already carries `state` (added to `Thread::toArray()` in Story 1.2) to the relay for ordinary replies, not just the four lifecycle-verb system messages Story 1.4 touched. This file is **not modified** by this story; it is read and traced only, to confirm AC7 is satisfied by existing infrastructure once revival happens before this event fires.

### Assumption — the "single shared helper" AC3 names is the revival mutation, not a new pre-save id-resolution function (documented, no interactive user available)

AC3's "the effective thread id is resolved once through the single shared helper, before the write" is AD-2's language, which also governs Story 1.6's Locked-write guard (where "before the write" is load-bearing: a refusal after `commentsManager->save()` is not a refusal). For *revival*, there is no such correctness requirement on the comment write itself — but there **is** one on the event dispatch that follows it (see AC7's trace above). Two readings were available: (a) introduce a brand-new private id-resolution method in `ChatManager`, called before `commentsManager->save()` in both methods, replacing their current (structurally different) resolution logic; or (b) reuse each method's own already-resolved, already-shared `$threadId`/`$isThread` pair — computed once, at the point both methods already call the one method they have in common (`updateLastMessageInfoAfterReply()`) — and add one new shared mutation method (`ThreadService::reviveIfClosed()`) that both call with that value.

**Resolution:** (b). Rationale: `sendMessage()` resolves `$threadId` pre-save (via the reply branch's `validateThread()` or the explicit-parameter branch) while `addSystemMessage()`'s parameter-driven pre-save value and its post-save `topmost_parent_id`-derived value can differ in shape; forcibly unifying *how* each method arrives at its id is real, structural surgery this story does not need to do, since both methods already converge on one identical, already-shared value (`$isThread`-gated `$threadId`) by the time `updateLastMessageInfoAfterReply()` returns — before either method's event dispatch. Reading it a second time from a new helper would be the actual anti-pattern AD-2 warns against ("never on a value re-derived afterwards"). Story 1.6 AC2 explicitly owns closing `sendMessage()`'s remaining explicit-`threadId`-branch `validateThread()` asymmetry as its own, separately-scoped task — this story does not pre-empt that.

### Assumption — AC5's "the post is refused" is not yet literally achievable in this story's scope (documented, no interactive user available)

No write-refusal guard for a Locked Thread exists yet — Story 1.4's own Dev Notes flagged this explicitly: *"this story ships a Locked state that does not yet refuse anything... Stories 1.6 and 1.7 complete FR-5... and the epic does not ship without both."* Confirmed by reading `lib/Chat/ChatManager.php` in full: neither `sendMessage()` nor `addSystemMessage()` inspects `Thread::STATE_LOCKED` anywhere today. Story 1.5 therefore cannot make a post into a Locked Thread fail — that mechanism is Stories 1.6/1.7's seam (AD-2). This story's real, verifiable scope for AC5 is the *other* half of the sentence: the asymmetry is deliberate, meaning **revival itself** must never treat Locked the same as Closed. `ThreadService::reviveIfClosed()`'s `getState() !== Thread::STATE_CLOSED` guard is precisely that: a post that reaches a Locked Thread today (because the refusal guard does not exist yet) does not flip it to Ongoing, and once Stories 1.6/1.7 land, such a post will not reach `ChatManager` at all. Flagged here explicitly rather than silently narrowing AC5, matching Story 1.4's own precedent for documenting epic-sequencing gaps.

### Race/idempotency note (documented, no interactive user available)

The PRD's adversarial review (`_bmad-output/planning-artifacts/prds/prd-clavis-spreed-2026-08-08/review-adversarial.md:123-130`, against an earlier draft) flagged a race between a reply-triggered revival (FR-3) and a concurrent manager lock (FR-4/FR-5): "nothing makes the read-state-then-write atomic." AD-13 ("Last write wins, and the response is the correction") is this codebase's general, already-adopted resolution for Thread-state concurrency: no optimistic-concurrency token, no conflict response, mutations apply unconditionally, and every mutator ends by *removing* (never re-setting) the cache entry — so the next reader always re-derives from the database rather than from a possibly-superseded in-memory copy. `reviveIfClosed()` inherits this by construction (it delegates entirely to `changeState()`, which already follows AD-13): if a lock and a revival race, whichever `threadMapper->update()` call lands last in the database wins, and the next cache miss reads that value — no special coordination is added or needed by this story, and none is required by any AC. Both `reviveIfClosed()` (this story) and `changeState()` (Story 1.4) are also naturally idempotent under retry: re-running either against an already-Ongoing Thread is a no-op.
