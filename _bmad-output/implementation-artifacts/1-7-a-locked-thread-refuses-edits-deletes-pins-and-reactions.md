# Story 1.7: A Locked Thread refuses edits, deletes, pins and reactions

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a participant,
I want a Locked Thread to be frozen rather than merely closed to new messages,
so that nobody edits an existing message to say something new in a Thread that is supposed to be settled.

## Acceptance Criteria

**AC1**
**Given** `ReactionManager` and `ChatManager`'s own edit, delete and pin methods reach `commentsManager->save()` without passing through `sendMessage()` or `addSystemMessage()`
**When** Locked is extended to them
**Then** it is done by a **third enforcement seam** covering all four, not by four separate controller guards and not by an extra entry in the exemption list.

**AC2**
**Given** a Locked Thread containing a message the actor wrote
**When** they attempt to edit it
**Then** it is refused with the `ThreadLocked` identifier.

**AC3**
**Given** a Locked Thread containing an existing message
**When** a participant or a moderator attempts to delete it
**Then** it is refused.

**AC4**
**Given** a Locked Thread containing an existing message
**When** a moderator attempts to pin or unpin it
**Then** it is refused.

**AC5**
**Given** a Locked Thread containing an existing message
**When** a participant attempts to add or remove a reaction
**Then** it is refused, and `ReactionManager` is a call site of the third seam.

**AC6**
**Given** the Thread is unlocked by a Thread Manager
**When** all four operations are retried
**Then** all four succeed again.

**AC7**
**Given** the seam is one place
**When** a new route to `commentsManager->save()` is added in future
**Then** it routes through the seam rather than around it.

## Dev Notes

### Why this story is not "add four more entries to Story 1.6's guard"

Story 1.6 built exactly two enforcement seams inside `ChatManager` (`sendMessage()`, `addSystemMessage()`) for **new content**. Edit/delete/pin/unpin/react are structurally different: they mutate an **existing** comment (or create a lightweight reaction comment) directly via `commentsManager->save()`, never routing through either of those two methods for their *own* primary write (AC1's stated premise, confirmed by reading all six methods in full). This story is therefore a genuine **third** seam — the same underlying decision (`ThreadService::ensureNotLocked()`), reused verbatim, called from six new sites (four in `ChatManager`, two in `ReactionManager`) rather than from the two Story 1.6 already covers.

### A real, pre-existing defect this story's guard placement incidentally fixes

Since Story 1.6, `ChatManager::addSystemMessage()` already refuses on a Locked thread for **any** message type not in `Listener::THREAD_MESSAGE_TYPES_WITH_CONTEXT` — and `message_deleted`/`message_edited`/`message_pinned`/`message_unpinned`/`reaction_revoked` are not in that list. Because `deleteMessage()`/`editMessage()`/`pinMessage()`/`unpinMessage()`/`deleteReactionMessage()` all call their own primary `commentsManager->save()` **before** calling `addSystemMessage()` for their accompanying system message, a Locked thread today would already: (1) let the primary edit/delete/pin/unpin write succeed, (2) then throw `LockedException` from the *system message* call, uncaught, surfacing as an unclean error while the underlying data has already changed. This story's guard — placed as the **first statement** in each of the six methods, before any write at all — closes this gap as a natural consequence of correct placement, not as a separately-scoped bug fix. Do **not** "fix" this by adding these five verbs to the exemption list; that would make them bypass the guard entirely (the opposite of AC2-AC5), not close the partial-write gap.

### The threadId-for-a-comment formula (not new, already the codebase's own convention)

`(int)$comment->getTopmostParentId() ?: (int)$comment->getId()` is already used identically at ~15 call sites across this codebase (`lib/Controller/ChatController.php` ×6, `lib/Signaling/Listener.php` ×3, `lib/Service/BotService.php`, `lib/Model/Message.php`, `lib/Search/MessageSearch.php`, `lib/Controller/RoomController.php`) to resolve "the thread this specific comment belongs to, whether it is the thread root itself or a reply within it — or its own id as a harmless fallback when it belongs to no thread at all." That fallback is safe here because `ThreadService::ensureNotLocked()` (Story 1.6) already tolerates an unresolvable thread id as a silent no-op via `findByThreadId()`'s `DoesNotExistException` catch — a message's own id will essentially never coincide with a real, Locked thread id belonging to the same room. This story reuses the formula, it does not invent a variant of it.
