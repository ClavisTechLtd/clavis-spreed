# Clavis Talk — Thread Management and Navigation

## Why

**A pain to solve, at the scale the feature was built for.** A Clavis Talk room used seriously for work accumulates threads the way a shared inbox accumulates mail, and today every thread a room has ever produced sits in one undifferentiated list — sorted by nothing but recency, reachable only through the right-hand sidebar's "Shared items" and a three-item preview. A room with two hundred threads is a room where nobody uses threads, because finding the one you want costs more than starting a new one. The affected users are members and moderators inside customer organisations that self-host Clavis Talk; the trigger is GitHub issue `ClavisTechLtd/clavis-deploy#22`, which enumerates ten gaps. This work gives threads a lifecycle (done, shut, live), a front door (their own destination with search, filters and per-thread unread), and organisation (featuring, tags) — so threads become how a busy room organises itself instead of a feature people abandon. Clavis Talk is a fork of Nextcloud Talk (`clavis-spreed`, tracking `stable34` / Talk 24.0.3); threads themselves already ship upstream, so this specifies what upstream does not have and corrects one thing it does wrong.

## Capabilities

- **CAP-1 — Thread lifecycle**
  - **intent:** A Thread Manager can move a Thread between Ongoing, Closed and Locked, and any participant can see which state it is in wherever the Thread appears.
  - **success:** A new Thread reports Ongoing; a Thread Manager closes and reopens it, and locks it from either state — optionally stating a free-text reason when locking — each recording a system message naming the actor, and the reason where one was given; a non-manager posting into a Closed Thread returns it to Ongoing with no state system message; a non-manager is refused on every direct transition; state renders on the Directory row, the thread header, the Thread Root Message and the Followed Thread List, with the Closed indicator conveying that posting is still permitted and reopens it, and the thread header showing the lock reason where one exists and no empty affordance where none does. Ongoing shows no badge.

- **CAP-2 — Locked refuses every write**
  - **intent:** While a Thread is Locked, no content reaches it and no existing content in it changes, from any entry point.
  - **success:** One integration scenario per write path — not one for the family — covering all nine enumerated paths (typed message; bot via API; in-process bot answer; rich object; poll; file share, which can also create Threads; attachment upload, which performs no thread validation today; message scheduled while Locked; message scheduled before locking, which fails visibly at fire time with a reason the sender can see) plus editing, deleting, pinning and reacting to existing messages — the last four reach the comments store by a route neither content choke point covers, so they ride one further enforcement seam that is mandatory, not optional. Every refusal is visible rather than silently redirected to main chat, is distinguishable by the client from a lack-of-permission failure and from a Thread-not-found failure, and carries the lock reason where one exists so the participant learns why at the point they hit the wall. Lifecycle system messages themselves still write.

- **CAP-3 — Thread Manager authority**
  - **intent:** Only the author of a Thread's root message or a moderator of its Conversation can change Thread State, feature a Thread, or set Thread Tags — the rule upstream already applies to renaming.
  - **success:** A root-message author succeeds on their own Thread without moderator rights; a moderator succeeds on any Thread in the Conversation; anyone else and any guest is refused with the same error shape across all three operation families; authority is re-evaluated per request, so a demotion between opening a menu and using it refuses the request; a non-manager sees no management controls at all rather than disabled ones; renaming behaviour and permissions are unchanged, verified by the existing integration coverage.

- **CAP-4 — Thread Directory**
  - **intent:** A participant can reach a Conversation's Threads as a first-class destination and, from that list alone, decide which one to open.
  - **success:** One click from the Conversation's top bar opens the Directory as a peer of the other sidebar surfaces — reachable by the same navigation, including on narrow viewports, without replacing the tab set; the Shared-items thread preview no longer exists; the default view shows Ongoing Threads plus every Featured Thread and nothing else, Featured first, then most-recent-activity first, updating live as replies arrive; state and tag filters combine and make clear that Threads are hidden rather than absent; the filter resets to Ongoing on returning to the Conversation; each row carries title, state, tags, reply count, last activity and unread count without a long title displacing any of them; the list pages incrementally while filtering and searching still span every Thread in the Conversation.

- **CAP-5 — Thread search by title**
  - **intent:** A participant can find a Thread by remembering its name, in the current Conversation and across the Followed Thread List, without falling back to reading messages.
  - **success:** Matching is case-insensitive, substring-anywhere and diacritic-insensitive, so `dinh dang` finds `Định dạng`; results appear as the participant types with no submit action; results span every Thread State and show state so a Locked match is not mistaken for a live one; a control handing the same term to the existing message search is present whether the title search returned zero, one or many results, and taking it does not lose the participant's place; Followed Thread List results identify their Conversation and follow the same matching rules.

- **CAP-6 — Featured Threads**
  - **intent:** A Thread Manager can raise a Conversation's standing references above everything else so they stop sinking as they stop generating replies.
  - **success:** A featured Thread appears above every unfeatured Thread for every participant in the Conversation, regardless of activity, state or the active filter, and a Closed or Locked featured Thread shows its state rather than being hidden; unfeaturing returns it to activity ordering and to the default filter's hiding rules; featuring never changes Thread State; a non-manager is refused; featuring past the server-side per-Conversation limit is refused with an error naming the limit, and the limit is stated in the interface before it is hit.

- **CAP-7 — Thread Tags**
  - **intent:** A Thread Manager can tag a Thread with free text carrying a colour, shared across the Conversation, so one room can separate several kinds of work.
  - **success:** An added tag is visible to every participant and removable per Thread without affecting other Threads carrying it; only editing is restricted, viewing is not; the first use of a tag text in a Conversation sets its colour from a bounded palette and every later use of that text — compared case-insensitively — takes the established colour without asking; the same text in another Conversation is independent; a Thread Manager can recolour a tag for the Conversation and every Thread carrying it updates without other participants reloading; typing offers the Conversation's existing tags with their colours and marks clearly when the input would create a new one; whitespace is stripped and empty input refused; a sixth tag on a Thread and a twenty-first distinct tag in a Conversation are each refused with an error naming the limit.

- **CAP-8 — Per-Thread unread state**
  - **intent:** A participant sees, per Thread, how many messages they have not read, independently of every other Thread and of the Conversation's main chat.
  - **success:** Reading Thread A leaves Thread B's count unchanged and does not change main-chat unread; reading the main chat to its end leaves the count unchanged in any Thread the participant has read before; counts exclude the participant's own messages and system messages; two participants who have read different amounts of one Thread get different counts; a participant who has never opened a Thread gets a count derived from their fallback baseline rather than the Thread's full length, so joining a room with five hundred old Threads raises no badge flood; a participant can mark one Thread read from its row without opening it and mark every Thread in the Conversation read including those hidden by the active filter; a rejoining participant inherits no stale per-Thread state; counts appear in both the Directory and the Followed Thread List, update live, distinguish an unread mention from unread replies — two-way only, with direct and group mentions not separated — and render capped rather than widening the row; opening a Thread with unread messages lands on the first unread message behind a boundary that does not jump, and leaving it part-read returns to the same place.

- **CAP-9 — Conversation unread splits from thread unread**
  - **intent:** The Conversation's unread message count means main-chat messages only, and the Conversation separately reports whether any of its Threads holds unread messages.
  - **success:** A Conversation whose only unread messages are thread replies reports zero unread messages and reports the thread-unread indication instead; a participant mentioned only inside a Thread is still reported as mentioned even at zero count — the specific regression this change would otherwise cause, because the mention indication is currently derived from that count; main-chat mentions behave exactly as today; reading a Thread does not decrease the Conversation count and reading main chat does; the thread-unread indication is raised by Threads hidden under the default filter, distinguishes unread thread mentions from unread thread replies and no further, is always clearable by CAP-8's mark-all, and is surfaced in the Conversation list without duplicating or contradicting the main-chat badge; the new semantics are announced through their own capability flag, separate from the thread-management flag.

- **CAP-10 — Notifications name the Thread**
  - **intent:** A recipient can tell from a notification which Thread it came from, and a Thread's followers learn when it is closed, locked or reopened.
  - **success:** Each of the nine notification subjects the server emits for in-thread activity carries the Thread Title, with a test per subject rather than one per family; notifications for activity outside a Thread are unchanged; an over-long title truncates without removing the message preview entirely; in a Conversation marked sensitive the Thread Title is withheld alongside the content already withheld; a subscribed follower is notified on close, lock and reopen naming the Thread, the actor and the lock reason where one was given, respecting their per-Thread notification level, while a non-subscriber is not notified; reopening by reply produces only the ordinary reply notification.

- **CAP-11 — Push payload identifier parity**
  - **intent:** A push payload about in-thread activity carries the same identifiers the in-app notification already carries, so a client can route without a second network call.
  - **success:** A push payload for in-thread activity contains both the message identifier and the Thread identifier in the same composed form the in-app notification uses, and one for activity outside a Thread contains the message identifier, which it does not today; the in-app identifiers are unchanged, verified by the existing integration assertion; a client parsing positionally does not misread the shorter value when no Thread identifier exists; a sensitive Conversation's payload carries identifiers but neither the Thread Title nor a lock reason — an identifier names a destination without disclosing what is in it; acting on a notification opens the Thread with the message in view, opens a Locked Thread showing its state with the composer disabled, and lands a deleted Thread's notification in main chat with an explanation rather than an error; a maximum-length title with a maximum-length preview is still delivered, with the title preserved and the preview shortened when both cannot fit, truncated only on boundaries valid for Vietnamese text. **This capability changes almost nothing a user can see on the clients this work touches** — web and desktop deep-linking already works, and Android already reaches Threads by fetching the notification over the API. It exists as groundwork for the mobile epic.

- **CAP-12 — Thread navigation and addressability**
  - **intent:** A participant can reach the Directory from where they already are, and a Thread or the Directory has an address they can copy, share and return to.
  - **success:** Entry points exist in the Conversation top bar (present only where the server supports thread management, indicating unread Threads, keyboard reachable and screen-reader announced with purpose and unread state), in the thread header alongside the existing route back to main chat, and on the Thread Root Message as a route distinct from the existing route into the Thread, opening the Directory positioned on that row; a message link inside a Thread still opens that Thread at that message; the Directory has an address that reopens it on the same Conversation; reloading with a Thread open restores that Thread; browser back and forward move between main chat, Thread and Directory in visit order; every address either renders or degrades cleanly in the surfaces served by the secondary router factory, with which of the two it does declared per address.

## Constraints

- **The fork has no plugin seam.** `clavis-spreed` must keep taking upstream Nextcloud Talk releases, and Talk offers no extension point for thread semantics, message-send interception or list surfaces — so upstream files are edited directly. New behaviour lands in new classes wherever a seam allows; edits inside upstream-owned methods are the smallest diff that works and carry a comment naming the requirement. Restoring full git history (`git fetch --unshallow`) is a prerequisite of the first commit, not part of the work.
- **The OCS API is additive-only, with exactly one recorded exception.** No field removed, renamed or given a new meaning — except CAP-9's redefinition of the Conversation unread count and the mention indication derived from it. Nothing else may cite that as precedent. The composed notification object identifier is append-only, variable-arity and absence-significant: a trailing position may be appended, never reordered or shortened, never padded, never a sentinel, and `0` is never valid at any position. Thread endpoints are undocumented outside the generated OpenAPI specification, so every new endpoint appears there and in its generated TypeScript types, regenerated in the same change rather than as a follow-up.
- **Two capability flags, both in `FEATURES` and `LOCAL_FEATURES`.** One for thread management, one for CAP-9's unread semantics; the shipped unconditional `threads` flag is reused for neither. `features-local` is the only channel through which a client learns a feature does not work over federation, so a `FEATURES`-only declaration makes federation degradation unimplementable.
- **Every Thread mutation invalidates the cache; only the read path repopulates.** Thread data is served from a distributed cache with a 900s lifetime and negative caching. Mutators call `remove()`, never `set()` — re-setting from the entity a mutator happens to hold republishes a value a concurrent write already superseded and pins it for the full TTL. A missed invalidation makes a state change succeed for the actor and revert for everyone else. This is the highest-risk correctness surface in the work.
- **One write seam per layer.** `ThreadService` is the sole writer of thread rows and the thread cache; tag tables are a separate aggregate owned solely by the tag service. `ChatManager` is the sole place thread write policy is enforced for posted content, with a third seam required for edits, deletes and pins, which reach the comments store by other routes. On the client, one Pinia store owns Thread state and is the only caller of the transport layer.
- **Scale is a deliberate design target, adopted rather than observed.** Every list surface stays usable at ≥1000 Threads and 200 participants per Conversation. The room that prompted the work holds roughly 180 Threads, so this is a safety margin that costs nothing — keyset paging is no more expensive than the offset paging that would not scale. No request does work proportional to the Conversation's total Thread count; unread for a page resolves in a fixed number of queries independent of page size, counting stops at the display cap + 1, and pages are addressed by a keyset cursor on the total order rather than an offset. The client keeps the server's order and never re-sorts.
- **Per-participant thread state grows with engagement, not with participants × Threads.** A per-Thread read marker is the one genuinely new source of row growth, written on a hot path every time a participant reads further. Rows exist only for Threads a participant has actually read, are never created merely by joining, and are reclaimed when a participant leaves a Conversation. This is the cost that plausibly drove upstream to create these columns and drop them three weeks later, so real growth is measured against participants × Threads before a customer meets it, not assumed bounded.
- **Migrations are additive, defaulted, re-runnable, and backfill nothing.** Customers self-host and upgrade in place with no maintenance window. No table-wide `UPDATE` runs at upgrade. Every pre-existing Thread reads as Ongoing, unfeatured and untagged on day one — the accepted limitation, not a bug.
- **Thread Titles, Thread Tags and lock reasons carry message-grade sensitivity.** They are withheld wherever the shipped sensitive-conversation setting already withholds message previews, reusing that mechanism rather than paralleling it. Routing identifiers are not content and do travel. No Thread Title or lock reason enters any part of a push payload outside the envelope the customer's server encrypts for the target device: the Clavis push proxy stays unable to read what it relays, which is a commitment made to customers.
- **Federation degrades by omission, never by broken controls.** No new Thread field is proxied and no new Thread endpoint is exposed through the federation proxy; the client hides state, featuring, tag and per-Thread-unread affordances on a federated Conversation rather than rendering inert ones.
- **Concurrency resolves by last-write-wins, and the response is the correction.** No optimistic-concurrency token and no conflict response. The client replaces its local copy with the mutation response, never with what it sent; other participants converge through the relayed state-change system message, not polling.
- **Every lifecycle verb is registered in six places.** Four of them sit inside one signalling listener file, so they are extracted into named constants declared together and each site tests membership. Two decide whether a message relays at all; two decide whether it arrives carrying its Thread. The relay set is a superset of the Locked-guard exemption list, and the lifecycle-transition subset *is* that exemption list.
- **Four database engines, including Oracle.** CI tests MySQL/MariaDB, PostgreSQL, SQLite and Oracle on every PR. Write-time text normalisation, grouped unread queries and migrations must hold on all four; nothing may rely on the deployment's collation.
- **Accessibility, theming and Vietnamese are acceptance criteria, not polish.** State is never conveyed by colour alone — a Closed or Locked Thread carries a label or icon, and a Thread Tag always renders its text with its colour. Colours come from a bounded palette drawn from the host Nextcloud's design tokens, legible in light and dark at normal and high contrast; arbitrary colour input is not accepted. New surfaces are keyboard reachable and screen-reader announced. All new user-visible text is translatable; Thread Titles and Thread Tags are user content and never translated; Vietnamese must be correct in search matching, truncation and sorting.
- **The glossary is binding vocabulary.** PRD §3 fixes the terms downstream documents and code must use verbatim; introducing a synonym is a defect. Two terms were chosen against the obvious word to avoid colliding with shipped Talk features: **Featured Thread** (not pinned — `pinned-messages` ships) and **Thread Tag** (not label — `conversation-tags` ships, and is per-user and private where Thread Tags are shared within the Conversation).

## Non-goals

- **Not a task tracker.** Thread State describes the state of a conversation, not assignment, due dates, priority or a status workflow. A Closed Thread means the talking stopped, not that work finished.
- **Not a moderated taxonomy.** Thread Tags are free text by explicit choice. No tag administration surface, no per-Conversation approved set, no renaming a tag across Threads, no merging, no hierarchy — deferred to v2, with input suggestion as the v1 mitigation.
- **Not private organisation.** Featuring and tags are shared within the Conversation. Personal bookmarks, personal tags and per-participant ordering are excluded by design, not deferred.
- **Not automatic lifecycle.** No auto-close after inactivity, no auto-archive, no scheduled cleanup. Every state change is a person deciding.
- **Not bulk operations.** Closing, tagging or featuring many Threads at once was offered as a mitigation for the day-one limitation and declined by the requester. Deferred to v2.
- **Not migration-time reclassification.** No migration closes or archives existing Threads; declined by the requester.
- **Not federation.** Thread state, featuring, tags and unread counts are unspecified across federation boundaries; upstream does not support thread message fetching over federation at all.
- **Not the mobile clients.** Android and iOS adoption of the corrected payload, and the Android push fallback fix where the reported symptom actually originates, are a separate epic that depends on this one shipping.
- **Not a thread permission system.** Thread Managers derive from existing authority. No per-Thread participant list, no per-Thread role, no delegating management of one Thread.
- **Not threads-of-threads.** A Thread has one level; replying inside a Thread does not create a sub-Thread.
- **Not bots as Thread Managers.** Bots create Threads and post into them as they already do; they do not change Thread State. Put to the requester and excluded by decision, not by omission — reopening it means first deciding which bots would qualify, which nobody has asked for.

## Success signal

Before release, on a Conversation seeded to the design target — a thousand Threads, two hundred participants, activity spread across a year — a moderator reduces the Directory's default-filter list to twenty Threads or fewer using only row-menu interactions, and a returning participant finds an unread Thread, answers in it, and watches that badge clear while the others hold and reading the main chat clears none of them. The Directory's first-page response time does not regress against a baseline captured on the current nested list against the same fixture, and per-participant read-marker rows track Threads actually read rather than participants × Threads. The person who filed issue #22 is walked through both demonstrations and says, without qualification, that this is what they asked for.

Two failure modes leave no trace in a fixture and no query anyone at Clavis can run, so they are watched rather than measured, and the first report of either is treated as the signal rather than an isolated complaint: a Conversation unread badge reported wrong on an unmodified Android, iOS or desktop client after the unread split ships; and a room where locking has become routine rather than exceptional, or where the twenty-tag ceiling is being hit.

## Assumptions

- Every product-level `[ASSUMPTION]` in the source PRD stands as written except three, which were put to their owner and resolved — reactions as writes, identifiers as routing, and the reference deployment. PRD §16 is the confirmable index of all twenty-three, marked accordingly, and is not restated here. The highest-leverage live one is unchanged: the personas and user journeys are inferred from the issue text and repository context, with no customer interviews, tickets or usage data behind them.
- **The seeded fixture is representative enough to accept against.** It reproduces the mechanism, not the social behaviour of a real room — uneven Thread lengths, reply patterns, who talks to whom — so the success signal demonstrates that the feature works, not that people will use it. Nothing available substitutes for that, and the day-one limitation stands: a customer upgrading sees every pre-existing Thread as Ongoing until someone closes them by hand.
- `prd.md` and `addendum.md` are carried as adopted companions rather than absorbed and retired, because their per-requirement testable consequences and existing-code map retain downstream value for epics, stories and implementation. The kernel above lifts the five-field content; it does not replace them.
- `ARCHITECTURE-SPINE.md` is treated as decided and binding for every technical seam this SPEC names. Where its rules and the PRD's prose differ on a mechanism, the spine wins; where they differ on intent, the PRD wins.
- The pre-work Directory response-time baseline the success signal depends on has not been captured yet, and the seeded fixture it must be captured on does not exist yet. Both are work in the first Directory story, not later measurement.
- CAP-11 is verifiable at payload construction only. The Clavis push proxy's delivery hop to Apple and Google is unimplemented and blocked on credentials Clavis does not hold, so no downstream plan may assume an on-device push test exists.
- The push payload size budget has not been measured. CAP-10's title and CAP-11's budget requirement proceed on the stated policy — title preserved, preview shortened — with the measurement as acceptance criteria inside the notification story rather than a gate before epics are cut. If the measurement comes back tighter than the policy assumes, that requirement changes and nothing else does.
